# Framework integration, safety, and test-infrastructure research

**Research date:** 2026-08-24  
**Target release:** 0.6.0  
**Scope:** Next.js, Astro, SvelteKit, React Router/Remix-style resource routes,
Express, generic Fetch-response frameworks, package installation shapes,
runtime safety, and framework-level CI.  
**Related research:**
[Social-network metadata and preview compatibility](./0.6.0_social-network-metadata.md)

## Executive summary

Metaplate's low-level integration strategy is sound: a standard `Response`
travels cleanly through modern server frameworks, and raw bytes cover classic
Node frameworks and build scripts. The current evidence does not justify all
of the README's framework claims, however. Unit tests prove Metaplate's own
functions, while examples are only typechecked against source aliases. Except
for one Next-specific unit test and an unpromoted spike, CI does not build or
run real framework applications from the packed npm artifact.

Three concrete 0.6.0 issues deserve priority:

1. **Dimension-changing Resvg options break a documented invariant.** A local
   reproduction using `resvg.fitTo: { mode: "width", value: 600 }` rendered
   600x315 pixels while `plate.size` and metadata still claimed 1200x630.
2. **The generic handler only supports precomputed copy.** `handler(copy)`
   ignores framework request/context arguments, so it cannot safely derive
   copy from dynamic route params without a wrapper at every call site.
3. **Runtime support is underspecified.** `metaplate/node` uses Resvg's native
   Node binding. A SvelteKit or Astro route is supported on a Node-compatible
   adapter, not automatically on Cloudflare Workers, Deno, or another edge
   runtime merely because that framework returns Web `Response` objects.

The release should establish framework testing infrastructure before adding
more named framework claims. Tests should install the packed artifact into
minimal fixture applications, run each framework's real production build,
start server-mode fixtures where applicable, fetch the generated page/image,
and validate HTML metadata, status, headers, detected image format, and actual
dimensions.

## Current integration surface

### Framework-neutral core

- `metaplate` builds image descriptors and OG/X-shaped metadata without a
  renderer.
- `metaplate/render` uses Satori and emits SVG text.
- `metaplate/node` uses Satori plus native Resvg and returns `Uint8Array`,
  `RenderedPixels`, or a Web `Response`.
- `createNodeOg().handler(copy)` closes over copy and returns a zero-argument
  function that ignores any arguments a framework supplies.
- `metaplate/next` delegates rendering to Next's `ImageResponse`.

### Documentation and examples

- The README explicitly names Next.js, Astro, SvelteKit, Remix, and Express.
- The repository contains full-looking example source only for Next and Astro.
- `tsconfig.examples.json` maps `metaplate/*` imports to source files. This is
  useful API drift coverage, but it does not run Astro or Next's compiler,
  bundler, route analysis, static exporter, or runtime.
- SvelteKit, React Router/Remix, and Express have no fixture application.
- Express has a build-script example but no actual Express response example.

### Existing CI evidence

The CI is already strong at the package and native-library layers:

- Node 20, 22, and 24 are exercised.
- Linux, Windows, and macOS exercise Resvg's native packages.
- Actions are pinned by full commit SHA and workflow permissions are minimal.
- `npm ci --ignore-scripts`, dependency review, and high-severity audit checks
  reduce supply-chain exposure.
- The packed artifact is installed into temporary consumers.
- Optional-peer errors, declaration isolation, real Satori/Resvg rendering,
  encoder agreement, and CLI behavior are tested.

What is missing is the layer between the package artifact and real framework
build/runtime behavior.

## Framework-by-framework findings

### Next.js

**Current fit:** Strongest integration, but still under-tested as a framework.

Next officially supports generated `opengraph-image` and `twitter-image`
files, route handlers returning `Response`, route params for dynamic image
files, and `generateImageMetadata` for multiple images. Current Next 16 passes
`params` and generated image IDs as promises. Its static export supports static
GET route-handler responses but not handlers that depend on incoming request
data.

Metaplate currently uses a custom `/og-image/route.tsx` example rather than
fully adapting the metadata-file convention. This is useful for explicit file
extensions and base paths, but it leaves integration work to the consumer:

- exporting `size`, `contentType`, and alt in special metadata files;
- adapting promised Next 16 params to copy;
- using `generateImageMetadata` for variants;
- handling the documented shallow replacement of nested Open Graph fields;
- selecting static export versus runtime rendering.

**0.6.0 recommendations:**

1. Build real Next 15 and Next 16 fixtures from the tarball.
2. Test both a static exported route handler and a server-rendered dynamic
   route.
3. Add a documented special-file adapter example whose default export calls
   `plate.render`, and validate its generated tags.
4. Decide whether `createNextOg` should expose a small helper for the special
   file convention rather than asking users to re-export three values
   manually.
5. Exercise Next's `params: Promise<...>` convention so the adapter cannot
   silently freeze on an older framework signature.

### Astro

**Current fit:** The `Response` primitive is correct for both static and SSR
endpoints, but only the static example exists and it is not built in CI.

Astro's official endpoint contract is a `GET(context)` function returning a
Web `Response`. In static mode Astro calls it during the build and writes a
file whose extension comes from the endpoint filename; in SSR mode an adapter
executes it per request. Astro encourages typing with `satisfies APIRoute`.
Dynamic static routes use `getStaticPaths`; runtime routes receive params from
the endpoint context.

`og.handler(copy)` works for the repository's constant-copy static route
because JavaScript permits ignored arguments. It does not consume Astro
`params`, `props`, or `request`, and the example does not prove `APIRoute`
assignability.

**0.6.0 recommendations:**

1. Build the current static Astro example using the packed artifact and verify
   the emitted `.png` path, headers/host behavior, bytes, and dimensions.
2. Add a dynamic/SSR Node-adapter fixture using `params` to resolve copy.
3. Type route exports with `satisfies APIRoute`.
4. Explicitly document that `metaplate/node` requires a Node-compatible Astro
   adapter; an Astro Cloudflare deployment is not covered.

### SvelteKit

**Current fit:** Response-compatible on Node, but documentation currently
overstates what has been proven.

SvelteKit `+server` files export HTTP-method functions taking `RequestEvent`
and returning `Response`. That makes Metaplate's response result a natural fit.
The deployment runtime still depends on the selected adapter. `adapter-node`
is compatible with `metaplate/node`; an edge adapter is not implied to support
native Resvg.

The current zero-argument handler can be assigned as a static GET function,
but dynamic copy requires a wrapper:

```ts
import type { RequestHandler } from "./$types";

export const GET: RequestHandler = ({ params }) =>
  og.response({ title: titleFor(params.slug) });
```

That wrapper is straightforward, but it means the README's “same handler
shape” wording is only true for closed-over copy.

**0.6.0 recommendations:**

1. Add an `adapter-node` fixture with a typed `RequestHandler` and dynamic
   param-derived copy.
2. Add a prerendered/static fixture if the release promises static SvelteKit
   output.
3. State the Node-adapter requirement beside the example.

### React Router framework mode / Remix migration path

**Current fit:** The primitive fits current resource routes; the naming and
example are stale or absent.

Current React Router framework-mode documentation uses a resource route with
no default component. GET is handled by `loader(args)`, and externally
consumed resources should return an explicit Web `Response`. This is exactly
the result of `og.response(copy)`, but the function name is `loader`, not
`GET`. A wrapper is required for route params.

Because modern Remix applications are converging on React Router framework
mode, 0.6.0 documentation should use current React Router terminology and note
the equivalent Remix resource-route pattern instead of making a broad untested
“Remix” promise.

**0.6.0 recommendations:**

1. Add one current React Router resource-route fixture built from the tarball.
2. Use loader args to derive copy and verify the fetched image.
3. Either add a tested Remix compatibility fixture or reword the support claim
   as React Router/Remix-style resource routes.

### Express

**Current fit:** Raw bytes are appropriate, but the README does not actually
show the HTTP adapter it names.

Express does not consume Web `Response` directly. The robust bridge is to
convert the returned `Uint8Array` to `Buffer`, set the exact content type and
cache policy, and send it through Express:

```ts
app.get("/og-image.png", async (_request, response, next) => {
  try {
    response.type(og.contentType);
    response.set("Cache-Control", "public, max-age=86400");
    response.send(Buffer.from(await og.render(copy)));
  } catch (error) {
    next(error);
  }
});
```

An async error path must reach Express error handling; examples that omit it
encourage hanging requests or unhandled rejections depending on framework
version and wrapper shape.

**0.6.0 recommendations:**

1. Add a minimal Express 5 fixture, start it on an ephemeral port, fetch the
   route, and verify headers/bytes/dimensions.
2. Publish the explicit `Buffer.from` bridge and error path.
3. Do not add an Express runtime dependency merely to remove six lines of
   adapter code.

### Generic Fetch-response frameworks

Hono, Elysia, Fastify Web-response bridges, serverless functions, and other
frameworks may accept or adapt Web `Response`, but support should be described
by capability and runtime:

- **Response-compatible + Node runtime:** plausible and covered by the generic
  API contract.
- **Response-compatible + edge runtime:** not supported by `metaplate/node`.
- **Raw Node response framework:** use `render()` bytes and an adapter.
- **Next runtime:** use `metaplate/next`.

Named support should require a real fixture or be clearly labeled as an
untested recipe.

## Concrete correctness and safety audit

### Confirmed: output dimensions can disagree with metadata

`NodeOgDefinition.resvg` exposes `fitTo` and `crop`. `createNodeOg` always uses
the SVG definition size for `plate.size` and metadata, while Resvg can change
the raster dimensions.

Confirmed reproduction on 2026-08-24:

```json
{
  "plateSize": { "width": 1200, "height": 630 },
  "pixels": { "width": 600, "height": 315 },
  "metadata": { "width": 1200, "height": 630, "type": "image/png" }
}
```

This contradicts the README statement that plate size, rendered bytes, and
metadata “can never disagree.” It is not a code-execution vulnerability, but
it can ship invalid social metadata and defeat the verifier if only the
declared size is used as the expected value.

**Recommended fix:** either remove dimension-changing Resvg options from the
public definition, reject them, or make the effective raster size the plate's
single authoritative size. Independently verify the rasterized dimensions
before encoding. `crop` needs its own regression cases.

### Operational risk: unbounded dynamic rendering

Rendering consumes CPU and memory, and `response()` buffers the complete
encoded image before constructing a response. A public route that turns
arbitrary query text, route parameters, remote images, or user-chosen sizes
into cards can become a cost-amplification or denial-of-service endpoint.

Metaplate currently fixes the canvas size at definition time, which is a good
boundary. It does not control:

- text length or component-tree complexity;
- concurrent render count;
- encoder output size;
- request timeout/abort behavior;
- cache cardinality;
- remote assets referenced by a Satori component.

**0.6.0 action:** add a “dynamic route safety” section and test that framework
examples use bounded copy, stable path keys, and explicit caching. Avoid a
query-string-driven example. Library-level concurrency or byte limits should
be considered separately because safe values are deployment-specific.

### SSRF risk when remote assets are user-controlled

Metaplate itself does not currently fetch page URLs or accept a remote asset
option. Satori/Next image components can fetch URLs embedded in the authored
component. If an application copies an untrusted URL into `<img src>`, the
server-side renderer may access internal services or cloud metadata endpoints.

**0.6.0 action:** document that remote asset URLs must be allowlisted and must
not come directly from request input. Any future remote social-page verifier
requires explicit SSRF controls: reject loopback/private/link-local addresses,
re-resolve each redirect, limit schemes/ports/redirects/bytes/time, and avoid
forwarding credentials.

### Native-runtime mismatch

Resvg is a native Node dependency. Importing or bundling `metaplate/node` into
Workers/Edge runtimes may fail at build time or deployment even though those
runtimes implement Web `Response`.

**0.6.0 action:** publish a runtime matrix and add a deliberate edge-build
negative test or a clear diagnostic. Framework name alone is insufficient;
the adapter/runtime is part of the compatibility contract.

### Package peer shape may install React unnecessarily

`react` is a non-optional peer in `package.json`, while the package documents
metadata-only and plain-object/React-free consumers. npm 7+ installs peer
dependencies by default; npm does not automatically install peers marked
optional. The current package verification checks that Satori, Resvg, and Next
stay absent from a lean consumer, but it does not make the same assertion for
React in that first install shape.

**0.6.0 action:** explicitly test a metadata-only tarball installation for the
absence of React. If the test confirms installation, mark React optional and
retain first-use guidance where JSX/Next actually needs it. Test npm's modern
peer resolution rather than relying only on declaration isolation.

### Overbroad peer ranges create unsupported future claims

The current ranges (`next >=15`, `satori >=0.33.3`, `@resvg/resvg-js >=2.6.2`)
have no upper bound. They imply compatibility with future breaking majors that
CI cannot currently know about. This is especially risky for the Next adapter
and pre-1.0 Satori API.

**0.6.0 action:** test the declared minimum and current supported line. Either
cap the ranges at the next breaking boundary or establish a process that adds
support and expands the range only after a green fixture. A scheduled
allowed-to-fail latest-framework job is useful early warning, not evidence for
an unbounded published peer range.

### Positive safety findings

- Current `npm audit` reports zero known vulnerabilities across the installed
  dependency graph as of the research date.
- Image path construction rejects traversal-like dot segments, queries,
  fragments, backslashes, control characters, invalid origins, and embedded
  credentials.
- Package font names and lexical paths are constrained to the selected package
  directory; caller-supplied package resolver hooks remain trusted code.
- Known custom encoder formats are signature-checked, and wrong encoder return
  types fail at the boundary.
- `Content-Type` is set after caller headers, so a configured header cannot
  silently override the format Metaplate advertises.
- Optional peers load lazily and preserve non-missing dependency errors rather
  than misdiagnosing every import failure.
- CI uses pinned actions, minimal permissions, dependency review, audit, and
  cross-platform native-library tests.

## Proposed framework testing infrastructure

### Core principle: test the artifact consumers install

Every framework fixture should consume a tarball produced by `npm pack`, not
TypeScript path aliases into `src`. The sequence should be:

1. Run the normal source checks and build.
2. Pack the exact working tree into a version-independent artifact path.
3. Install that artifact into isolated fixture applications with locked
   framework dependencies.
4. Run the framework's production typecheck/build.
5. Start server-mode fixtures on an ephemeral localhost port where needed.
6. Fetch both a page and image route.
7. Verify emitted metadata URLs, status, cache/content headers, detected format,
   actual dimensions, and non-empty output.
8. Shut down the child process reliably and retain logs/artifacts on failure.

### Suggested fixture layout

```text
integration/
  framework-fixtures/
    next-15-static/
    next-16-server/
    astro-static/
    astro-node/
    sveltekit-node/
    react-router-node/
    express-5/
  scripts/
    pack-under-test.mjs
    run-framework-fixture.mjs
    verify-built-page.mjs
    verify-served-image.mjs
```

Keep fixture applications minimal: one page, one image route, one local font,
and one shared assertion contract. Do not turn examples into a monorepo demo
site; small fixtures make framework failures attributable.

### What every fixture must prove

- The packed package installs without reaching into the repository source.
- The fixture typechecks using framework-generated route types.
- The production bundler accepts optional/native dependency boundaries.
- The route is emitted at the expected filename/path.
- The response is 200 and its `Content-Type` matches detected bytes.
- Cache headers match the fixture's intended static/dynamic policy.
- Actual dimensions equal metadata dimensions and `plate.size`.
- Page HTML contains absolute, correctly prefixed OG/X image URLs.
- Static builds do not accidentally depend on request-only values.
- Dynamic params are resolved through typed framework context.

### CI tiers

#### Pull-request blocking

Linux/Node 20 or 22 is sufficient for the framework layer because native
cross-platform coverage already exists elsewhere. Run:

- current supported Next;
- Astro static;
- SvelteKit adapter-node;
- current React Router resource route;
- Express 5.

These fixtures should be deterministic and lock exact dependency versions.

#### Release blocking

Add:

- minimum declared Next version and current Next version;
- minimum supported Satori and Resvg peers plus current locked versions;
- Next static export and server runtime;
- Astro static and Node SSR;
- the packed-package install-shape tests, including React absence for a
  metadata-only consumer.

#### Scheduled compatibility canary

Run weekly against `@latest` framework releases with `continue-on-error` and a
visible issue/notification path. This detects ecosystem changes early but must
not make ordinary PRs nondeterministic. Once a version is claimed in peer
ranges, move it into the pinned blocking matrix.

### Avoid a full OS × Node × framework Cartesian product

The current native compatibility job already proves Resvg on Linux, Windows,
and macOS across supported Node lines. Framework builds mostly exercise
bundling and route conventions. Run them on Linux, then add a targeted Windows
framework case only if path behavior or a framework bug warrants it. This
keeps CI cost proportional to distinct failure modes.

1. Fix/restrict Resvg `fitTo` and `crop` so rendered and advertised dimensions
   cannot disagree.

3. Promote a real Next build into blocking CI, covering the declared minimum
   and current supported versions.
4. Build the existing Astro example for real.
5. Add explicit Node-versus-edge runtime documentation.
6. Test and correct the metadata-only React peer installation shape.
7. Replace unqualified named framework claims with tested runtime-specific

### P1 — intended 0.6.0 integration improvements

1. Add typed SvelteKit Node, React Router resource route, and Express 5
   fixtures.
2. Add a context-aware handler/resolver API or publish canonical wrappers:


   The API must support sync/async copy without tying core types to any one
   framework.
3. Add a Next special-file example/helper and promised-param coverage.
4. Validate page HTML and image routes together, including `basePath` and
   absolute metadata URL behavior.

1. Dedicated tiny adapters only where they materially improve types or error

2. Edge-native rendering research using a WASM-compatible renderer.
3. Streaming encoders/responses for large outputs.
4. Automated compatibility canary issue creation.
5. Bun and Deno runtime certification.

## Design guidance for a context-aware handler

A framework-neutral resolver overload can eliminate repetitive wrappers while
remaining decoupled from framework packages:

```ts
handler(copy)
handler((context) => copy)
handler(async (context) => copy)
```

Important constraints:

- Preserve the current closed-over-copy overload exactly.
- Infer the framework context structurally from the resolver parameter.
- Never treat a function-valued copy object as a resolver accidentally; an
  explicit `handlerFrom` name may be safer than an ambiguous overload.
- Propagate framework args rather than selecting only `Request`.
- Do not catch render errors generically; framework error handling needs the
  original cause.
- Allow the resolver to return a `Response` for early 404/authorization only
  if the type contract is explicit; hidden unions make route code harder to
  audit.
- Document validation for params and forbid direct unbounded query-to-render
  examples.

An explicit alternative is clearer:

```ts
handler(copy)                 // existing static/precomputed path
handlerFrom((context) => copy) // dynamic framework path
```

The plan phase should choose between overload ergonomics and the safer explicit
name after compiling real framework fixtures.

## Research maintenance note

Framework route conventions and runtime defaults change faster than the core
Web `Response` contract. Each named compatibility claim should record the
fixture version that proves it. Upgrade the fixture and documentation together;
do not let an unbounded peer range stand in for a tested compatibility policy.
