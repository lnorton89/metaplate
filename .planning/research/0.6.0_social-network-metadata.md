# Social-network metadata and preview compatibility research

**Research date:** 2026-08-24  
**Scope:** Potential Metaplate features for Facebook, Instagram, X/Twitter,
Discord, LinkedIn, Slack, Mastodon, Pinterest, and Microsoft Teams.  
**Target release:** 0.6.0  
**Status:** Product research feeding 0.6.0 planning; exact scope is not yet an
implementation plan.
**Related research:**
[Framework integration, safety, and test infrastructure](./0.6.0_framework-integration-and-test-infrastructure.md)

## Executive summary

Metaplate should not model every network as though it has a unique metadata
language. Most ordinary link previews fall into three families:

1. **Open Graph consumers:** Facebook, LinkedIn, Mastodon, and, in practice,
   many chat clients.
2. **Open Graph plus X Card consumers:** X has its own `twitter:*` namespace;
   Slack explicitly says its classic unfurler reads both Open Graph and X Card
   metadata.
3. **Richer structured or app-driven unfurls:** Pinterest can consume Open
   Graph or Schema.org for Rich Pins; Teams promotes Schema.org JSON-LD and
   app-driven Adaptive Cards; Slack and Discord also have app-specific ways to
   create richer embeds that are outside webpage metadata.

The best direction is therefore a **standards-first metadata model with
platform validation profiles**, not a collection of mostly duplicated
`discordMetadata()`, `facebookMetadata()`, and `instagramMetadata()` helpers.
Platform names are useful for verification, diagnostics, documentation, and
variant selection. They are usually the wrong primary abstraction for tag
generation.

The highest-value additions are:

1. Let Open Graph and X use different images and settings while preserving the
   current one-image convenience path.
2. Support ordered multiple Open Graph images and optional square/landscape
   variants.
3. Add crawler-oriented verification profiles: absolute HTTPS URLs, public
   fetchability, response MIME/bytes agreement, dimensions, file size, and
   platform-safe formats.
4. Prevent or loudly warn about publishing SVG as a universal social image.
5. Add optional page-level metadata (`title`, `description`, canonical URL,
   type, site/creator) without coupling the framework-neutral core to Next.js.

## Recommended 0.6.0 release boundary

The existing 0.6.0 black-box audit already identifies verifier hardening as
required release work. To keep the release cohesive, the recommended social
metadata slice is:

1. Add compatibility guardrails for social delivery formats, especially SVG
   and other formats not documented by selected targets.
2. Allow Open Graph and X to use separate image configuration while preserving
   today's shared default.
3. Make X card selection configurable for `summary` and
   `summary_large_image`, with optional site/creator identity.
4. Support ordered multiple Open Graph image descriptors.
5. Document production crawler requirements and expose target-aware checks
   through the existing verifier where they can operate on local artifacts.
6. Add tests and migration examples demonstrating that the 0.5 API remains
   source-compatible.

Remote page crawling, full page-level metadata generation, HTML serialization,
Schema.org, richer app/player/video cards, and multi-layout plate rendering
should remain stretch work or follow-on releases unless the core 0.6 verifier
work finishes with adequate margin. This boundary delivers meaningful network
configurability without turning 0.6.0 into a general-purpose SEO or unfurling
framework rewrite.

## What Metaplate does today

The current `src/core.ts` surface is intentionally small:

- `SocialImageDescriptor` contains `url`, `alt`, `width`, `height`, and
  optional `type`.
- `socialImageMetadata()` returns one descriptor under both
  `openGraph.images` and `twitter.images`.
- X/Twitter is fixed to `summary_large_image`.
- `origin` is optional, so metadata can contain relative image paths.
- There is no page title, description, canonical URL, Open Graph type,
  site/creator identity, multiple-image ordering, or per-channel override.
- Every plate exposes one size and one output format.
- `createSvgOg().metadata()` advertises `image/svg+xml` because the plate emits
  SVG.

This is a good zero-config common case, but the shared descriptor has become
the main configurability ceiling.

## Cross-platform conclusions

### 1. Open Graph is the common denominator

The Open Graph protocol defines image URL, secure URL, MIME type, width,
height, and alt text. It recommends `og:image:alt` whenever an image is
present. Metaplate already models most of the image descriptor correctly.

What is missing is the surrounding page object and ordered multiplicity. OGP
allows repeated properties; the first tag is preferred when consumers face a
conflict. That makes ordering part of the public API rather than an internal
detail.

### 2. “One image for every network” should remain a convenience, not a rule

A 1200x630 image is a strong landscape default and is extremely close to
LinkedIn's documented 1200x627 recommendation. However, Meta currently
recommends square creative for some placements, Pinterest supports multiple
images, and X may need its own crop/content treatment. Consumers should be
able to provide:

- a primary 1.91:1 landscape image;
- an optional square image;
- a separate X image or card type;
- ordered fallback images in conservative formats.

Metaplate does not need automatic platform detection at runtime. It needs a
declarative set of variants and deterministic metadata ordering.

### 3. PNG and JPEG are the safest universal delivery formats

Meta's current webpage-sharing docs list `image/jpeg`, `image/gif`, and
`image/png`. LinkedIn lists JPG, PNG, or GIF. This is direct evidence that the
existing `createSvgOg().metadata()` result is not a safe universal social
preview, even though SVG is valuable for rendering and downstream conversion.
WebP and AVIF should remain available renderer outputs, but a compatibility
profile must warn when the selected targets do not document them.

Recommended policy levels:

- `universal`: PNG or JPEG; absolute HTTPS URL; public fetch required.
- `openGraph`: structurally valid OG descriptor; broader formats allowed with
  warnings.
- named profiles such as `facebook` and `linkedin`: enforce documented format,
  size, and dimension rules.
- `custom`: caller-owned constraints.

### 4. Crawler readiness is more than valid image bytes

The existing verifier checks files. Social preview failures also come from the
page/image delivery boundary:

- relative image URL instead of a crawler-ready absolute URL;
- HTTP or mixed content where HTTPS is expected;
- authentication, bot protection, robots rules, or WAF challenges;
- a redirect to a different canonical URL;
- wrong `Content-Type` despite valid image bytes;
- HTML error response at the image URL;
- missing width/height, causing a slower or unreliable first share;
- a stale crawler cache after replacing bytes at the same URL.

Meta explicitly says its crawler caches the resolved canonical URL and
metadata, exposes re-scraping through Sharing Debugger, and advises using a new
URL when an image changes. A network-aware verifier should inspect a deployed
URL as well as local bytes.

### 5. Debug targets are valuable even when schemas are undocumented

Discord's official change log confirms an Embed Debugger. Meta has Sharing
Debugger. LinkedIn has Post Inspector. These should be emitted as human-facing
report links rather than automated scraping integrations, because authentication
and tool behavior can change.

## Recommended product shape

### A. Preserve the current API

Keep this zero-config path working:

```ts
socialImageMetadata("/docs", "Docs card", {
  origin: "https://example.com",
  imagePath: "og-image.png",
});
```

It should continue to produce one landscape image for OG and X with a large
summary card.

### B. Add explicit channel overrides

An additive shape could be:

```ts
socialImageMetadata("/docs", "Docs card", {
  origin: "https://example.com",
  imagePath: "og-image.png",
  openGraph: {
    images: [landscape, square],
  },
  twitter: {
    card: "summary_large_image",
    image: xLandscape,
    site: "@example",
    creator: "@author",
  },
});
```

Exact naming should be resolved during design, but the semantics should be:

- omitted overrides retain today's shared-image behavior;
- an override replaces only that channel's default;
- output arrays preserve caller order;
- descriptors are copied/frozen so later mutation cannot desynchronize tags;
- X card types form a discriminated union, preventing a player/app card from
  missing required fields.

Avoid adding `discord`, `facebook`, and `instagram` output objects when they
would merely duplicate `openGraph`.

### C. Add a page-level metadata builder separately

The image helper should stay small. A new `socialMetadata()` can own:

```ts
socialMetadata({
  title: "Metaplate",
  description: "Composable social image tooling",
  url: "https://example.com/docs",
  type: "website",
  images: [landscape, square],
  twitter: { card: "summary_large_image", site: "@example" },
});
```

The core result should be framework-neutral data. Adapters can translate it to
Next metadata or serialized HTML tags. Do not make Next's broad metadata union
the core public contract.

### D. Introduce verification profiles, not generation presets

Proposed command direction:

```sh
metaplate verify-url https://example.com/docs \
  --target universal \
  --target facebook \
  --target linkedin \
  --target discord
```

Suggested report sections:

- fetched page status, redirects, canonical URL, and content type;
- discovered OG and X tags in source order;
- image fetch status, redirects, bytes, MIME, dimensions, and file size;
- shared errors (missing title/image/absolute URL/alt);
- target-specific warnings and unsupported/undocumented claims;
- direct links to the relevant official debugger tools.

Profiles must distinguish three verdict classes:

- `error`: violates a documented requirement;
- `warning`: common interoperability risk or undocumented format;
- `unknown`: the network publishes no stable contract for the check.

That distinction prevents “works with Discord/Instagram” from becoming a
promise based on folklore.

### E. Add image variants after the metadata model

One plate currently owns one size. A later variant layer could reuse the same
copy and design function while exposing named outputs:

```ts
const social = createSocialPlates({
  landscape: { size: { width: 1200, height: 630 }, component },
  square: { size: { width: 1080, height: 1080 }, component: squareComponent },
});
```

Do not implement variants as silent center crops. Text-heavy social cards need
layout-aware reflow and safe zones, so separate components or a variant
argument are safer than automatic cropping.

## Prioritized 0.6.0 feature backlog

### P0 — required 0.6.0 compatibility and honest output

1. Document that SVG metadata is not a universal social-delivery choice.
2. Add a validation warning/error when raster-only target profiles receive
   SVG, WebP, AVIF, or an unknown format.
3. Add an opt-in “production/crawler-ready” check that requires an absolute
   HTTPS URL; do not change today's relative default in a patch release.
4. Add deployed image verification: HTTP status, redirect chain, declared
   MIME, detected bytes, dimensions, and file size.

### P1 — intended 0.6.0 metadata configurability

1. Separate OG and X image configuration while keeping the current shared
   fallback.
2. Make X card type configurable (`summary` and `summary_large_image` first).
3. Add X `site`, `siteId`, `creator`, and `creatorId`.
4. Support ordered multiple Open Graph images.
5. Add Facebook, LinkedIn, Slack, Mastodon, Discord, and generic profiles to
   the verifier. Mark Instagram as experimental/undocumented.

### P2 — 0.6.0 stretch or follow-on work

1. Add square/landscape plate variants and CLI batch verification.
2. Add a framework-neutral page metadata builder and HTML serializer.
3. Add optional Schema.org JSON-LD builders for Teams and Pinterest use cases.
4. Explore X player/app cards and OGP video/audio only as separately scoped
   features; they introduce hosting, security, and required-field contracts
   beyond an image library.
5. Add a generated compatibility report suitable for CI artifacts.

## Suggested implementation slices

1. **Compatibility guardrails:** documentation plus pure profile rules over an
   existing `SocialImageDescriptor`. No network calls required.
2. **Metadata overrides:** core types/tests only; preserve all existing output
   snapshots.
3. **Multiple images:** ordered descriptors, Next adapter coverage, HTML tag
   ordering tests.
4. **Remote verifier:** a new entry point/CLI path with injectable `fetch`,
   redirect limits, response-size limits, and no private-network access by
   default if exposed in a server context.
5. **Page metadata:** new builder/serializer after image overrides settle.
6. **Variant plates:** renderer work last, driven by concrete layouts rather
   than speculative target presets.

## Non-goals and traps

- Do not create fake `discord:*` or `instagram:*` HTML tags.
- Do not equate Discord webhook embeds with Discord's automatic URL embeds.
- Do not claim WebP/AVIF compatibility across networks merely because browsers
  support them.
- Do not promise pixel-identical previews; consumer UI, crops, cache, and
  heuristics change independently of metadata.
- Do not silently fetch arbitrary URLs from a hosted verifier without SSRF
  protections, byte limits, timeouts, and redirect limits.
- Do not make platform profile changes a semver-breaking change to the basic
  metadata helper; strict checking should be explicit.
- Do not add Schema.org, Adaptive Cards, Slack Block Kit, or Discord bot embeds
  to `SocialImageDescriptor`; they solve different layers of the stack.

## Open questions for planning

1. Should the core eventually return a standards-shaped object
   (`openGraph`/`twitter`) or a neutral object translated by adapters?
2. Is HTML tag serialization in scope for Metaplate, or should it only expose
   data for framework integrations?
3. Should remote verification live in the main CLI or an optional Node entry
   point to keep the metadata package dependency-free?
4. Does “multiple images” mean multiple independently rendered plates, or only
   metadata descriptors pointing to caller-managed assets in the first slice?
5. Which claims should CI keep current through live fixture pages and periodic
   manual debugger checks?

## Research maintenance note

Network preview behavior is a moving target. Before converting a rule into a
hard error, re-check the linked source and record the verification date in the
profile. Undocumented observations should expire into warnings unless a live
fixture or primary source reconfirms them.
