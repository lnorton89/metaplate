# 0.7.0 Socket dependency-alert remediation research

**Research date:** 2026-08-24  
**Target release:** 0.7.0  
**Input:** [Socket alerts for `metaplate@0.6.0`](https://socket.dev/npm/package/metaplate/alerts/0.6.0?tab=dependencies)  
**Status:** Exact Socket scores/alerts remain blocked by authentication; reproducible official-report import is now available and no dependency changes are justified without that evidence.

## Executive summary

The linked Socket page exposes the package alert surface, but its server-rendered
HTML does not include the individual alert rows in a fetchable response. The
page confirms the package/version context, not the exact alert names or affected
transitive paths. Therefore this document does **not** pretend that every Socket
signal is a confirmed defect in Metaplate.

Socket's own documentation says its analysis covers risks that ordinary CVE
scanners can miss, including install scripts, native code, network/filesystem/
shell access, obfuscation, telemetry, ownership changes, and dependency URLs.
Those signals are especially relevant to Metaplate because its development and
release graph intentionally contains native rendering packages and many
framework fixtures.

The local evidence currently shows:

- `npm audit --json` reports zero known vulnerabilities in the installed lockfile
  graph as of the research date.
- `@resvg/resvg-js`, `sharp`, Next SWC, Astro compiler, and other packages bring
  platform-specific native binaries or optional Wasm/native packages. Native
  code is expected for the renderer/tooling, but it needs explicit review and
  platform coverage rather than blind suppression.
- CI already disables lifecycle scripts (`npm ci --ignore-scripts`), runs high
  severity npm audit, uses dependency review, pins GitHub Actions by SHA, and
  verifies package signatures/provenance after publication.
- `package.json` uses a broad `overrides.esbuild` rule and the lockfile pins the
  current resolved graph. Any override is a containment mechanism, not proof
  that the upstream package is safe or semver-compatible.
- The published package has no ordinary runtime `dependencies`; renderer peers
  are installed by the consumer. Socket may still report the package's peer and
  development graph, or capabilities of packages reachable from the package
  release/fixture workflow. The scope must be separated into published runtime
  risk and repository CI/build risk.

## Socket alert interpretation

Socket's official categories relevant to this project are:

| Signal | What it means | Metaplate-specific interpretation | Default action |
| --- | --- | --- | --- |
| Critical known malware / typosquat | Strong evidence of a compromised or impersonating package | Stop release; identify exact package/version/path immediately | Remove/quarantine, rotate exposed credentials, rebuild from clean lockfile |
| High install scripts | Package executes lifecycle code during install | Existing CI intentionally disables scripts; native packages may still require review for functionality | Prefer script-free install; allow only documented, reviewed packages in isolated jobs |
| High Git/GitHub/HTTP dependency | Dependency is not fully registry/lockfile reproducible | Conflicts with reproducible release policy | Replace with registry tarball or immutable digest/commit, then verify provenance |
| High telemetry/network/shell/obfuscation | Package has behavior beyond a simple library surface | May be legitimate in frameworks/build tools but is risky in published runtime | Classify by dependency path and runtime reachability; remove or isolate if unnecessary |
| Medium native code | Compiled code is present | Expected in Resvg/Sharp/SWC/compiler tooling; risk is platform/binary trust, not automatically malware | Pin, inspect package provenance, test all supported OS/CPU paths, document rationale |
| Medium recently published/new author/ownership | Higher change or takeover risk | Important for release-time updates, especially renderer/framework packages | Cooldown and review before promotion; do not automatically reject established packages |
| Low env/filesystem/dynamic require | Capability signal, not proof of vulnerability | Common in Node tooling and font/image loading | Review reachable code and avoid treating low signals as release blockers alone |

Sources:

- [Socket supply-chain risk alerts](https://docs.socket.dev/docs/supply-chain-risk)
- [Socket FAQ and analysis model](https://docs.socket.dev/docs/faq)

## Confirmed project facts

### Package/runtime graph

The current manifest declares no regular `dependencies`. It declares renderer
peers (`satori`, `@resvg/resvg-js`, `react`) and an optional Next peer. The
repository's dev graph includes Next, Astro, React Router, Express, Vite,
TypeScript tooling, Resvg, and Fontsource. This is a large **development and
fixture** graph, not necessarily the graph a normal metadata-only consumer
installs.

Notable native or platform-specific packages in the lockfile include:

- `@resvg/resvg-js@2.6.2` and platform-specific Resvg packages;
- `sharp@0.35.3` pulled by framework tooling/Next optional dependencies;
- Next SWC platform packages;
- Astro compiler bindings and Wasm fallback packages;
- other framework/compiler packages with optional native or Wasm targets.

The project already tests native rendering across Linux, Windows, and macOS,
and package verification uses the exact packed artifact with lockfile-verified
local peers. That evidence supports retaining native rendering, but it does not
close an alert against a specific package until the alert path is known.

### Existing controls

- `npm ci --ignore-scripts` in CI and release verification;
- `npm audit --audit-level=high` in CI and release verification;
- pull-request dependency review failing on high severity;
- Dependabot weekly npm and GitHub Actions updates;
- immutable SHA-pinned GitHub Actions;
- package contents/export checks;
- packed-package consumer tests;
- registry signature and SLSA provenance verification;
- lockfile-based dependency copying for framework fixtures;
- no provider SDK or runtime service dependency in the published package.

These controls are good baseline containment. They do not replace Socket review,
because Socket analyzes package behavior and maintainer/metadata signals that
CVE databases may not contain.

## Remediation decision tree

For each Socket row, record this minimum tuple before changing anything:

```text
alert type
package and exact version
path from metaplate root
published-runtime or dev-only reachability
introduced-by version/change
Socket evidence URL or export
npm audit status
replacement/candidate versions
verification result
```

Then apply:

1. **Known malware, typosquat, or confirmed exploit:** block release, remove the
   package/path, invalidate and rotate credentials if the package executed in a
   credentialed environment, and rebuild from a clean checkout and lockfile.
2. **Vulnerability with a fixed version:** upgrade the smallest affected direct
   dependency or add a temporary exact override only when the fixed version is
   compatible and tests prove it. Prefer the upstream fix over a permanent
   override.
3. **Install script/native binary alert:** determine whether the package is
   required at runtime or only for fixtures/builds. Keep scripts disabled for
   audit/verification; if a script is genuinely required, run it only in a
   narrowly isolated job and document the package, script, reason, and outputs.
4. **Git/HTTP dependency:** replace it with a registry version or immutable
   source reference with integrity verification. Never normalize a mutable URL
   by merely accepting the alert.
5. **Telemetry/network/shell/filesystem/dynamic code:** inspect the exact code
   path and whether it ships in the npm tarball. Remove unused packages,
   configure opt-outs, or isolate the tool. A legitimate framework capability
   should be documented with a reason and not silently ignored.
6. **Native code/recent author/ownership/low capability:** treat as a review
   item unless combined with stronger evidence. Pin versions, preserve the
   lockfile, verify signatures/provenance where available, and retain only
   packages needed for supported workflows.

## Candidate remediation options

### Option A — minimize published install surface

Keep framework tooling and all renderer peers as peer/dev dependencies; ensure
`files` excludes fixtures and test-only assets; make metadata-only consumers
install no renderer packages if npm peer behavior allows the intended contract.

**Benefits:** lowers consumer exposure and Socket's published dependency
surface; preserves framework-neutral core.  
**Risks:** peer auto-install behavior and the current one-command renderer
promise must be re-tested; moving peers optional would be a semver/API decision.

**0.7 recommendation:** audit and measure first; do not change peer shape solely
from an unexpanded Socket page.

### Option B — reduce and isolate development graph

Move framework fixture dependencies to isolated fixture manifests or workspaces,
so the root package's release/build graph does not unnecessarily carry every
framework. Keep only the dependencies needed by normal tests in the root.

**Benefits:** fewer transitive alerts and faster review; clearer production vs
fixture risk boundary.  
**Risks:** more fixture orchestration; package verification must still install
exact packed artifacts and preserve current certification.

**0.7 recommendation:** strong P1 candidate if alert paths are dev-only and
multiple framework packages dominate the report.

### Option C — replace or pin flagged packages

For an affected package with a compatible maintained release, update the direct
dependency and lockfile through Dependabot-style review. Use `overrides` only as
a temporary, issue-linked containment measure and remove it after upstream
ranges accept the fixed release.

**Benefits:** smallest code change; preserves APIs.  
**Risks:** overrides can hide incompatibilities and may cause duplicate or
unsupported dependency resolutions.

**0.7 recommendation:** P0 for confirmed vulnerabilities/malware; test across
Node 20/22/24 and native OS matrix before release.

### Option D — replace native rendering/tooling

Investigate a Wasm/edge renderer or alternate image stack.

**Benefits:** reduces native-binary alerts and broadens edge deployment.  
**Risks:** substantial rendering/font compatibility work; changes output,
performance, and runtime guarantees; Socket's native-code flag alone is not
sufficient justification.

**0.7 recommendation:** research only/P2. Do not replace Resvg for a generic
alert without evidence of compromise or an unacceptable deployment defect.

## Proposed 0.7.0 scope

### P0 — evidence and release safety

1. Obtain/export the individual Socket alert rows for `metaplate@0.6.0` and
   record exact package/version/path, rather than relying on the opaque page.
2. Add a dependency inventory report separating:
   - packages included in the published tarball;
   - runtime peer packages consumers install;
   - dev-only framework/fixture packages;
   - native/platform-specific packages;
   - packages with install scripts or remote/Git dependencies.
3. For each high/critical alert, produce a disposition: upgrade, replace,
   remove, isolate, or accepted-with-evidence. No high/critical alert should
   be silently ignored in release notes.
4. Re-run npm audit, lockfile integrity checks, package packing, and the existing
   packed-consumer/native framework tests after remediation.
5. Preserve a clean-install test with lifecycle scripts disabled and a separate,
   explicit test for any package that genuinely requires installation behavior.

### P1 — structural improvements

1. Split framework fixtures into isolated manifests/workspaces if the alert
   graph is dominated by dev-only dependencies.
2. Add a CI dependency report that emits package paths and native/script/remote
   capability facts as an artifact.
3. Add Socket or equivalent supply-chain status to the release checklist, with
   an exception record containing owner, reason, expiry, and verification.
4. Add a scheduled review for recently published or changed-owner packages used
   by release tooling.
5. Update the README/release notes only with user-impacting dependency changes;
   keep internal alert dispositions in `.planning/research` and release audit
   artifacts.

### P2 — follow-on research

1. Prototype an edge/Wasm rendering route independently of the native Node API.
2. Evaluate reducing the root development graph without weakening packed-package
   certification.
3. Compare Socket findings against npm audit, GitHub dependency review, and
   registry provenance to identify blind spots and duplicate noise.

## Recommended release policy

- **Block:** Socket critical known malware, possible typosquat, confirmed active
  exploit, mutable Git/HTTP dependency in a shipped path, or unexplained package
  behavior that executes during release with credentials.
- **Require remediation or signed exception:** high alert in a published/runtime
  path, high alert in a package executed by release/publish tooling, or a native
  package whose provenance/version/platform path cannot be explained.
- **Review and document:** medium/low capability alerts on expected Node,
  framework, compiler, font, or native image packages.
- **Do not claim “Socket clean” from npm audit:** npm audit covers known
  vulnerabilities; Socket also reports behavior, metadata, and maintainer risk.

## Exact report acquisition attempt

The official Socket CLI was invoked through the documented command path:

```text
npx --yes @socketsecurity/cli package shallow npm metaplate@0.6.0 --json
```

Socket returned `Auth Error` and required an API token. The same applies to the
corresponding deep `package score` command. No token is present in the
repository or local environment, and credentials must not be committed or
invented. Therefore the exact shallow/deep scores, alert rows, dependency paths,
and lowest-scoring packages cannot be truthfully populated in this document.

A reproducible importer is now available:

```sh
npm run socket:report -- socket-score-report.json socket-export.json
```

It accepts an official Socket JSON export for `metaplate@0.6.0`, preserves the
reported shallow/deep scores and alerts, records official provenance, and rejects
missing/untrusted sources or a different package version. The release gate must
remain incomplete until that input is supplied; `npm audit` is not a substitute
for Socket analysis.

## Evidence gaps

The linked Socket page cannot be used from this research run to identify the
individual rows because its alert data is rendered outside the extracted page
text. Before implementation, capture one of:

- Socket's exported JSON/report;
- the alert table copied from the authenticated UI;
- a screenshot with package names, versions, paths, and severities;
- Socket CLI/API output for the exact version.

Without that evidence, changing dependencies would risk fixing the wrong
package, breaking the supported framework matrix, or weakening the package's
one-command install contract.

## Conclusion

The project already has unusually strong npm/CVE and release-artifact controls,
and the current npm audit is clean. The correct 0.7.0 work is to make Socket's
behavioral alerts actionable: recover the exact alert paths, classify published
versus dev-only reachability, remediate every high/critical finding, isolate
fixture tooling where practical, and document justified native/Node capability
signals. A blanket downgrade, mass dependency replacement, or permanent
`overrides` rule is not supported by the evidence currently available.
