# 0.7.0 deployment-route research

**Research date:** 2026-08-24  
**Target release:** 0.7.0  
**Status:** Discovery research; not an implementation plan.  
**Related research:** [0.6.0 framework integration research](./0.6.0_framework-integration-and-test-infrastructure.md)

## Question

How should Metaplate document and, where necessary, support the popular ways
users deploy generated Open Graph images and dynamic image routes?

The key distinction is not the hosting brand. `metaplate/node` depends on the
native Node Resvg binding, while static output and `metaplate/render` have a
different runtime story. A deployment route must therefore be described by:

1. build-time static generation;
2. Node-compatible server/serverless execution; or
3. edge execution, which is not supported by `metaplate/node` merely because it
   implements Web `Request`/`Response`.

## Executive summary

0.7.0 should add a deployment guide and a small set of tested route recipes,
not provider-specific adapters. The existing API already covers the useful
bridges:

- write `render()` output into a static site's public/build directory;
- return `response()`/`handler()` from a Node-compatible Fetch route;
- use `render()` and `Buffer.from()` for classic Node/Express handlers;
- use `metaplate/next` for Next's native `ImageResponse` pipeline.

The highest-value routes are:

| Route | Recommendation | Why |
| --- | --- | --- |
| Vercel Node.js Functions / Next.js Node runtime | **P0 documented and certified** | First-party fit for Next and Node functions; Vercel's Node runtime provides complete Node API compatibility. Do not use Edge runtime with `metaplate/node`. |
| Netlify Functions / framework-generated Node functions | **P0 documented and certified** | Netlify functions use a Node runtime and support custom paths; generated framework functions require project-level settings rather than function-file config. |
| Static export on Netlify, GitHub Pages, and similar CDNs | **P0 documented; certify static artifact** | Build-time rendering avoids native runtime deployment. GitHub Pages publishes static files but cannot run server-side languages or set custom per-file MIME headers. |
| Railway / Render / generic Node web service | **P1 documented recipe** | Straightforward long-lived Node process; useful fallback for Express and framework SSR. Include `PORT`, start command, health/shutdown behavior, and cache headers. |
| Cloudflare Workers / Vercel Edge / Netlify Edge | **P1 runtime boundary only** | Web APIs are not enough. Native Resvg cannot be assumed to bundle or execute. Document static generation or a separate edge-native renderer as the supported alternatives; do not claim an adapter without a real renderer fixture. |

The release should prefer one provider-neutral deployment matrix plus concise
provider pages. Provider docs change frequently, so every claim should include
the tested provider/runtime/version and an official link.

## Evidence gathered

### Vercel

Official Vercel Node runtime documentation says Node-powered functions support
all Node.js APIs and can expose either `/api` functions with Web Standard
exports/method exports or a captured `server` entrypoint. This matches both
`og.handler(copy)` and an Express/Node bridge. Vercel separately documents an
Edge runtime; that is not evidence that native Resvg works there.

Sources:

- [Vercel Functions](https://vercel.com/docs/functions)
- [Vercel Node.js runtime](https://vercel.com/docs/functions/runtimes/node-js)
- [Vercel runtimes](https://vercel.com/docs/functions/runtimes)
- [Vercel Edge runtime](https://vercel.com/docs/functions/runtimes/edge)

### Netlify

Netlify's Functions configuration docs state that the Node.js function runtime
is based on the Node version used for the build. Functions have default
`/.netlify/functions/<name>` paths and support custom paths, HTTP method filters,
and path parameters. The docs also note that framework adapters generate
function files at build time, so project-level settings should be used rather
than adding in-source config to generated functions. Current documented limits
include a default 1024 MB memory allocation and a 60-second synchronous limit;
these are deployment constraints worth surfacing for image generation.

Sources:

- [Netlify Functions configuration](https://docs.netlify.com/build/functions/configuration/)
- [Netlify Functions overview](https://docs.netlify.com/build/functions/overview/)
- [Netlify Next.js deployment](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/)
- [Netlify Express deployment](https://docs.netlify.com/build/frameworks/framework-setup-guides/express/)

### Cloudflare Workers

Cloudflare documents a subset of Node APIs, including native and shimmed APIs;
unsupported APIs may import but throw when called. Workers also support
WebAssembly, but this does not make the native `@resvg/resvg-js` binding a
Workers renderer. A future edge route requires an explicitly tested
Wasm/edge-compatible rendering implementation and its own font/asset loading
contract.

Source:

- [Cloudflare Workers Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)
- [Cloudflare Workers WebAssembly](https://developers.cloudflare.com/workers/runtime-apis/webassembly/)

### GitHub Pages

GitHub's documentation says Pages publishes static files and recommends a
GitHub Actions workflow for custom build processes or non-Jekyll generators.
It does not support server-side languages. GitHub Pages supports many MIME types
but does not permit custom MIME types per file/repository. Therefore static
`.png`/`.jpg` files are the safe route; extensionless dynamic route-handler
output is not a portable Pages deployment.

Sources:

- [Creating a GitHub Pages site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)
- [Configuring a publishing source](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
- [GitHub Pages HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)

### Railway and Render

Railway documents GitHub, CLI, template, and Dockerfile deployment routes for
Express and detects normal Node start commands. Render documents a Node web
service with build/start commands and automatic deploys from Git. Both are good
examples of generic Node services rather than reasons to add vendor SDKs.

Sources:

- [Railway Express guide](https://docs.railway.com/guides/express)
- [Render Node/Express guide](https://render.com/docs/deploy-node-express-app)
- [Render web services](https://render.com/docs/web-services)

## Proposed documentation structure

### 1. Deployment matrix

Add a README section or linked `docs/deployment.md` covering:

| Deployment shape | API | Required runtime | Output path | Status |
| --- | --- | --- | --- | --- |
| Static build | `render()` / `renderSvg()` | Build machine with Node and renderer peers | `public/og-image.png` or `.jpg` | Supported; easiest for Pages/CDN hosts |
| Vercel/Netlify Node function | `handler()` or `response()` | Node function runtime | Framework route or function path | Supported recipe; provider limits apply |
| Railway/Render Node service | `response()` or raw bytes | Node web service | App route | Supported recipe |
| Next.js native route | `metaplate/next` | Next Node runtime or supported Next build | Route handler / metadata file | Supported with existing Next claims |
| Edge function | Not `metaplate/node` | Edge/Wasm-compatible renderer required | Provider route | Not supported by current native renderer |

Every recipe should state that generated images are buffered, rendering is CPU
and memory intensive, and dynamic routes need bounded copy, stable cache keys,
timeouts/concurrency controls, and allowlisted local/remote assets.

### 2. Static hosts

A static-host recipe should use a real filename extension, render during the
provider's build command, copy into the published directory, and use
`socialImageMetadata` with an absolute origin/base path where required. For
GitHub Pages project sites, explicitly account for the repository subpath and
verify the final HTML/image URL. For Netlify, document `_headers` or
`netlify.toml` only when an extensionless route is intentionally used; an
extensionful file is preferable because static hosts infer its MIME type.

### 3. Node serverless

Use a provider-neutral handler first:

```ts
import { og } from "./og.js";

export const GET = og.handlerFrom(({ params }) => ({
  title: boundedTitle(params.slug),
  alt: `${params.slug} card`,
}));
```

Then map it to Vercel `/api` and Netlify Functions using each provider's route
convention. The guide should not import provider SDKs merely to return a Web
`Response`. Include a raw `render()` + `Buffer.from()` variant for Express.

### 4. Long-lived Node service

Document `npm run build`, `npm start`, `PORT`, graceful shutdown, and a health
endpoint. Railway and Render should be examples of this shape, not separate
Metaplate integrations. Ensure fonts and native dependencies are included in
the production install and that the service does not assume a writable working
 directory at request time.

## 0.7.0 implementation/research backlog

### P0 — documentation and certification

1. Add a deployment matrix and provider-neutral runtime decision tree.
2. Add Vercel Node and Netlify Node recipes with official links and explicit
   non-edge guidance.
3. Add static-host recipes for Netlify and GitHub Pages, including extensions,
   build output, `origin`, and `basePath`.
4. Add a packed-artifact fixture for at least one Vercel-style Web Standard
   function and one Netlify-style function, if their local runners can remain
   deterministic and dependency-light.
5. Verify generated static files and emitted page metadata together.
6. Add a release evidence table recording provider/runtime versions and what is
   actually certified.

### P1 — useful follow-on support

1. Add a generic Node-service fixture covering `PORT`, health, shutdown, and
   dynamic image fetches.
2. Add Railway and Render deployment snippets only after the generic service
   contract is stable.
3. Add CI checks that ensure docs' provider claims link to current official
   pages and that examples use the packaged artifact where feasible.
4. Provide a diagnostic error when a native Node entry point is bundled for an
   unsupported edge runtime, if this can be done without false positives.

### P2 — separate design work

1. Research and prototype an edge-native/Wasm renderer; do not silently swap
   rendering engines under the existing Node API.
2. Evaluate provider-specific adapters only if they materially improve route
   typing or deployment correctness.
3. Explore streaming/async rendering only with measured provider limits.
4. Certify Bun and Deno separately rather than implying support from Web APIs.

## Non-goals

- No Netlify/Vercel/Railway/Render SDK dependency in Metaplate core.
- No claim that all framework adapters on a provider share the same runtime.
- No Edge/Workers support for `metaplate/node` without a real tested renderer.
- No automatic deployment, account provisioning, or provider configuration.
- No provider-specific image URL rewriting; callers own public origin and
  deployment `basePath`.

## Research maintenance

Re-check provider runtime names, limits, and build conventions before each
release. Provider claims should be versioned in fixture manifests and should
expire to “documented recipe” rather than remain “certified” when fixtures stop
running.
